## Slide 09: Kode: useEffect dengan try, catch, finally

_fetch hanya gagal kalau jaringan putus. Status 404 atau 500 tetap dianggap berhasil, makanya kita cek res.ok._

**Kode:** Checkpoint 3: tambah state loading dan error

**Di slide:**
- Fungsi async ambilPosts di dalam useEffect
- if (!res.ok) throw new Error(...)
- catch mengisi error, finally mematikan loading

**Naskah:**

> Ini isi useEffect-nya. Perhatikan if not res.ok. Ini sering terlewat: fetch itu cuma gagal kalau jaringan putus.
>
> Kalau server balas 404 atau 500, fetch tetap dianggap berhasil, jadi kita cek res.ok sendiri.
>
> Finally dipanggil di akhir, berhasil atau gagal, untuk mematikan loading.

## Slide 15: Sifat 6: Request yang Tertinggal dan Balapan

_Dua masalah yang diselesaikan oleh satu mekanisme: cleanup dengan AbortController._

**Kode:** Checkpoint 4: batalkan request dengan AbortController.

**Di slide:**
- Cleanup effect: komponen hilang sebelum respons tiba, atau effect diulang (misalnya Strict Mode di development)
- Race condition: respons lama datang belakangan dan menimpa yang baru

**Naskah:**

> Sifat keenam. Effect punya cleanup, yaitu fungsi yang dijalankan React saat komponen hilang atau saat effect diulang. Di development, React Strict Mode bisa membuat effect diulang, jadi kalau kakak kadang melihat request terkirim dua kali di mode dev, itu bukan bug.
>
> Lalu ada race condition: pengguna pindah halaman sebelum respons tiba, atau respons lama datang belakangan dan menimpa yang baru.
>
> Solusinya sama: batalkan request lama di cleanup.

**Catatan untuk pengajar:** Pada uji di project ini (Next 16.2.10, mode dev webpack) effect hanya terlihat berjalan sekali, jadi request ganda tidak selalu muncul. Slide sengaja tidak menjanjikan dua request. Kalau muncul di laptop kakak, jelaskan sebagai Strict Mode.

## Slide 18: Apa Itu SWR?

_Library kecil berupa hook React untuk fetch data di client, dibuat oleh tim Vercel (pembuat Next.js)._

**Kode:** Checkpoint 5: fetch di Client Component dengan SWR

**Di slide:**
- Nama: stale-while-revalidate
- Cara kerja: tampilkan data dari cache seketika, fetch ulang di belakang layar, perbarui tampilan
- Bonus: cache bersama, request tidak dobel, revalidate otomatis

**Naskah:**

> Capek menulis semua itu? Dokumentasi Next.js merekomendasikan library seperti SWR atau TanStack Query.
>
> SWR itu library kecil berupa hook React, dibuat oleh tim Vercel, yang juga membuat Next.js. Namanya singkatan dari stale-while-revalidate: stale artinya data lama yang masih tersimpan di cache, revalidate artinya ambil data terbaru di belakang layar.
>
> Jadi cara kerjanya: tampilkan data lama dari cache seketika, fetch ulang di belakang, dan kalau data baru tiba, tampilan diperbarui.
>
> Bonusnya, cache bersama, request yang tidak dobel, dan revalidate otomatis.

**Aksi di kode dan browser:**
1. Di terminal: bun add swr

## Slide 21: Membaca useSWR: Key, Fetcher, dan Hasilnya

_Tiga bagian dari satu baris useSWR("/api/posts", fetcher)._

**Kode:** Tidak ada perubahan kode.

**Di slide:**
- Key: nama pengenal data di cache, biasanya URL
- Fetcher: fungsi yang kita tulis, dipanggil dengan key
- Hasil: data, error, isLoading

**Naskah:**

> Mari baca useSWR-nya. Ada tiga bagian.
>
> Pertama key, yaitu /api/posts: nama pengenal data di cache, biasanya berupa URL-nya. Komponen dengan key sama berbagi data dan request.
>
> Kedua fetcher: fungsi yang kita tulis sendiri, SWR memanggilnya dengan key sebagai argumen.
>
> Ketiga hasilnya: data, error, dan isLoading, pengganti tiga useState manual tadi.

## Slide 22: Kapan Fetch di Client Masuk Akal?

_Pegangan: kalau data dibutuhkan sejak halaman pertama tampil, jangan fetch di client._

**Kode:** Tidak ada perubahan kode.

**Di slide:**
- Cocok di Client: pencarian dan autocomplete, load more dan filter dinamis, data yang terus diperbarui
- Lebih baik di Server: konten utama halaman, halaman yang butuh SEO, data yang butuh secret atau database
- Opsi lain dari docs: ambil di Server, oper Promise ke Client, baca dengan use()

**Naskah:**

> Jadi kapan fetch di client itu masuk akal? Kalau datanya baru dibutuhkan setelah interaksi: pencarian, autocomplete, load more, atau data yang terus diperbarui.
>
> Kalau datanya dibutuhkan sejak halaman pertama tampil, lebih baik di server. Itu yang kita bahas di video berikutnya.
>
> Ada juga opsi ketiga dari dokumentasi: ambil di server, oper Promise ke client, baca dengan use. Kita bahas lebih lanjut nanti.
